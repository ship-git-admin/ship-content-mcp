# 端末の署名による認証（ship-content-mcp-req-v1 / res-v1）

パスワードを通信に乗せずに、MCP の入口へつなぐための決まりです。WordPress 側（`src/Security/SignatureCodec.php`・`SignatureAuth.php`）と中継プログラム（`bridge/ship-content-mcp-bridge.mjs`）は、この決まりで作っています。

## なぜ必要か

- WordPress の Application Password は HTTPS でしか使えず、HTTP で送ると盗み見られたときにそのまま漏れます。
- サーバーの Basic 認証と Application Password は、どちらも `Authorization` ヘッダーを使うため、両方は送れません。
- この方式は `Authorization` を使わず、秘密鍵は端末から出ません。サーバーには公開鍵だけを置きます。

## 鍵

| 鍵 | 持つ人 | 置き場 |
|---|---|---|
| 端末の鍵（Ed25519） | PM の端末ごと | 秘密鍵は端末（接続コードの `setup` か `keygen` で作る、権限 600）。公開鍵は WordPress の「端末の鍵」に登録 |
| サイトの鍵（Ed25519） | WordPress | 秘密鍵は DB のオプション（自動読み込みなし、画面に出さない）。公開鍵は管理画面に表示し、中継プログラムに設定 |

公開鍵の形は、生の32バイトを base64 にした文字列（44文字）です。

## 端末の鍵の渡し方（2通り）

| 方式 | 流れ | 秘密の通り道 |
|---|---|---|
| 接続コード（おすすめ・0.6.0 から） | 管理者が管理画面（または `wp ship-content-mcp keys issue`）で発行 → PM に DM → PM は `setup --clipboard` で読ませる | サーバーで鍵の組を作り、公開鍵だけを登録。種はコードに入れて1回だけ表示し、サーバーには残さない。管理者と DM を通る |
| keygen | PM が `keygen` で作る → 公開鍵を管理者に送る → 管理者が登録して、入口・鍵 ID・サイトの公開鍵を返す | 端末から出ない（より堅い） |

どちらも、通信に乗るのは1回ごとの署名だけで、秘密そのものは流れません。

### 接続コードの形

`shipmcp1.` の後に、次の JSON を base64url（`=` なし）にしたものを続けます。文章の中にあっても、中継プログラムは `shipmcp1.` から読み取ります。

| キー | 中身 |
|---|---|
| `v` | 1 |
| `site` | サイト名（表示用） |
| `name` | 短い英字の名前（設定のファイル名と、AI への登録の名前 `ship-content-<name>` に使う） |
| `url` | MCP の入口（管理者は https の入口に変えてよい。パスは変えない） |
| `key_id` | 端末の鍵 ID（`k` + 16桁） |
| `seed` | 端末の秘密鍵の種（Ed25519、32バイトの base64） |
| `server_key` | サイトの公開鍵（32バイトの base64） |
| `basic_auth` | （任意）サーバーの Basic 認証 `ID:パスワード` |

Claude デスクトップアプリの拡張機能（`.mcpb`、管理画面からサイトごとにダウンロード）では、接続コードを設定の欄に貼り、中継プログラムは環境変数 `SHIP_MCP_CODE` で受け取ります（拡張機能に入れたサイトの公開鍵と違うコードは止めます）。

`setup` は、これを `~/.ship-content-mcp/<name>.json`（権限 600）に保存し（秘密鍵は PKCS#8 の PEM）、つながるかを確かめます。`--register` を付けると Claude Code に登録します（`SHIP_MCP_CONFIG=<そのファイル>` だけを渡す）。コードの中身は画面に出しません。

## リクエスト

ヘッダー：

| ヘッダー | 中身 |
|---|---|
| `X-Ship-MCP-Key` | 鍵 ID（`k` + 16桁の16進。WordPress が登録時に決める） |
| `X-Ship-MCP-Timestamp` | UNIX 時刻（秒、10桁） |
| `X-Ship-MCP-Nonce` | 使い捨ての番号（base64url、22〜64文字） |
| `X-Ship-MCP-Signature` | 下の文字列への署名（base64、64バイト） |

署名する文字列（改行は `\n`）：

```
ship-content-mcp-req-v1
<METHOD（大文字）>
<Host（小文字、ポートを含む）>
<リクエストの URI（パスとクエリ、送ったとおり）>
<Timestamp>
<Nonce>
<鍵 ID>
<Mcp-Session-Id（なければ空）>
<本文の SHA-256（16進、小文字）>
```

サーバーが確かめる順：

1. MCP の入口の URL か（ほかの URL では、このヘッダーを無視する）
2. 形（鍵 ID・時刻・番号・署名・セッション ID）
3. 時刻のずれが ±300 秒以内か
4. 鍵が登録済みで、止められていないか。ユーザーがいるか
5. 署名が正しいか
6. 番号が初めてか（鍵ごとに 900 秒覚える。2回目は拒否）

どれかが違えば 401（`MCP-002`）。成功しても、REST の振り分けが MCP の入口でなければ 403 にします（URL の書き方で別の REST に届かせない）。その後、通常の権限の確認（専用の権限・低権限・IP・MCP が有効か）を行います。

## 応答

MCP の入口の応答には、サイトの鍵で署名を付けます。

| ヘッダー | 中身 |
|---|---|
| `X-Ship-MCP-Response-Signature` | 下の文字列への署名（base64） |
| `X-Ship-MCP-Server-Key` | サイトの公開鍵の指紋（16文字、確認用） |

```
ship-content-mcp-res-v1
<リクエストの Nonce>
<HTTP の状態（数字）>
<応答の Mcp-Session-Id（なければ空）>
<応答の本文の SHA-256（16進、小文字）>
```

中継プログラムは、署名がない・合わない応答を AI に渡しません（サーバーの Basic 認証の 401 など、WordPress より手前の応答は署名がないので、分かる言葉のエラーにします）。転送（リダイレクト）には従いません。

## 守れること・守れないこと

- 守れる：パスワード・秘密鍵の漏れ、リクエストの書き換え、使い回し（リプレイ）、別の URL への流用、応答の書き換え、端末ごとの停止。
- 守れない：**HTTP のときの中身の盗み見**（下書きの文章・写真・入力欄の構造）。HTTP の動作確認URLでは、公開予定の内容だけを扱ってください。本番は HTTPS で使ってください。
- 端末そのものが乗っ取られたときは、その端末の鍵を管理画面で止めてください。
- 接続コードは合鍵と同じです。届くまでの間（DM・メール）に漏れると、その PM として下書きを作れてしまいます。共有のチャンネルに貼らない、漏れたら止める、を守ってください（できるのは下書きの作成・修正だけで、公開・削除はできません）。
